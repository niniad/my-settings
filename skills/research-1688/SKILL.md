# research-1688

1688仕入先リサーチ → 工場問い合わせ・交渉 → サンプル絞り込み → サンプル評価・本発注判断。
**いつでも呼べる。** research-amazon-competitor でスペックマスタが定義済みであること。

## 開始前の確認

1. `/research-profit` で現在の利益試算を確認し、**仕入価格上限**（粗利率≥20%になる仕入単価）を取得する
2. 仕入価格上限を Phase 4 の Stage 1 フィルタ閾値として使用する

## ワークフロー

**スキル起動時は必ず企画プロセス管理テーブルを確認し、現在のフェーズとステータスをユーザーに提示してから作業に入る。**

```
Step 0: 対象商品の Base ID を確認 → 企画プロセス管理テーブルで進捗確認 → ユーザーに提示
Phase 4: 1688仕入先リサーチ → AliPrice CSV + agent-browser でサンプル候補を絞り込み
  → ユーザー サンプル候補確認 → 問い合わせ先決定
Phase 5: 商品ページ分析 + スペック対比表 → 工場問い合わせ・交渉 → チャットログ記録
  → ユーザー 追加質問/交渉継続
Phase 6: サンプル絞り込み・発注 → 総合評価レポート
  → ユーザー サンプル発注先決定
Phase 7: サンプル評価・最終判断
  → ユーザー 本発注 Go/NoGo → /research-profit で確定コスト利益計算
```

## 仕入先が見つからない場合のループ判断

| 状況 | 対処 |
|------|------|
| 価格差が小さい（目標との差 ≤20%） | スペック削減でコスト低減 → `/research-amazon-competitor` Phase 3 でスペックマスタ見直し → 再試行 |
| 価格差が大きい（差 >20%）または品質基準未達 | `/research-profit` で現状確認 → カテゴリー撤退判断（→ `/research-markets`） |

### 進捗管理ルール

- フェーズのステータス変更時は企画プロセス管理テーブルを更新する（ユーザー確認後）
- ステータス: `未着手` / `進行中` / `完了`

## Phase 4: 1688仕入先リサーチ

**目的**: 仕入候補を工場単位で網羅的に収集し、3段階フィルタリングでサンプル候補を絞り込む

> フィルタリング詳細: [references/filtering-process.md](references/filtering-process.md)
> ブラウザ自動化: [references/browser-automation.md](references/browser-automation.md)

### データ収集の2層構造

| 層 | データソース | 取得データ | 担当 |
|----|------------|-----------|------|
| **AliPrice TXT** | 👤 Chrome + AliPrice拡張 | タイトル・価格・年間販売数・工場基本情報（24項目） | 👤 手動エクスポート |
| **agent-browser 補完** | 🤖 商品ページ eval | 产品参数・SKU詳細・price_min/max・OEM指標・認証・详情テキスト | 🤖 自動巡回 |

### NocoDB テーブル構造

| テーブル | 段階 | 主なカラム |
|---------|------|-----------|
| **工場** | 概算 | 工場名, 店舗URL, 所在地, 入驻年数, 回头率, 商品数 |
| **商品** | 概算 | 商品ID, タイトル, URL, 画像URL, price_min, price_max, MOQ, 年間販売数, 工場リンク |
| **バリエーション** | 詳細 | SKU名, SKU画像URL, 単価, 在庫数, 商品リンク |

### ワークフロー

| # | タスク | 担当 | 詳細 |
|---|--------|-----|------|
| 4.1 | キーワード検索 → AliPrice TXT エクスポート | 👤 | 検索結果をTXTエクスポート（複数キーワードで繰り返し） |
| 4.2 | TXT → NocoDB 商品テーブル + 工場テーブルに登録 | 🤖 | AliPrice TXT をパースして一括登録。工場をユニーク抽出 |
| 4.3 | 候補工場ごとに全商品リスト化 | 👤 | AliPrice「店舗全商品」→スクロール→TXTエクスポート |
| 4.4 | 工場別TXT → NocoDB に追加登録 | 🤖 | 重複商品IDの検出・マージ |
| 4.5 | **Stage 1: 客観フィルタ** | 🤖 | price_max・年間販売数・除外KWで自動絞込（~1000→~200件） |
| 4.6 | **Stage 2: AI支援スクリーニング** | 🤖 | タイトル構造化・重複排除・画像URL重複検出（パクリ検出） |
| 4.7 | **Stage 3: 手動評価** | 👤 | Stage 2通過商品のみ目視確認（~50→~15件） |
| 4.8 | サンプル候補確定 | 👤+🤖 | 手動評価4以上を候補リスト化。工場ベースで5~7社を選定 |

### Stage 1 フィルタ閾値

Phase 4 開始時にユーザーと確認:
- **価格上限**: price_max で判定（利益シミュレーションから逆算、粗利率≥20%になる仕入単価）
- **価格下限**: カテゴリの品質担保下限（任意）
- **工場年間販売数下限**: 全工場の分布から極小を除外
- **除外キーワード**: 対象外の商品形態

## Phase 5: 商品ページ分析 → 工場問い合わせ・交渉

**目的**: ページ記載情報を事前把握し、**ページで確認できない項目だけ**工場に問い合わせる

> ページ分析の詳細: [references/page-analysis.md](references/page-analysis.md)
> チャットログ記録の詳細: [references/chat-log-analysis.md](references/chat-log-analysis.md)

| # | タスク | 担当 | 詳細 |
|---|--------|-----|------|
| 5.1 | 候補商品ページの自動巡回 | 🤖 | agent-browser で各商品URLを順次アクセス → `1688_extract.js` eval + screenshot --full |
| 5.2 | ページ情報の構造化 | 🤖 | `1688_extract.js` eval で产品参数・価格レンジ・OEM指標・認証等を自動抽出→NocoDB記録。画像内テキストは Gemini Vision OCR で中国語を読み取る |
| 5.3 | **Amazon競合 vs 1688スペック対比表** | 🤖 | スペックマスタの軸で Amazon競合（research-amazon-competitor 取得済み）と 1688候補を横並び比較。スペック適合スコア（優先度×充足率）を算出→NocoDB更新 |
| 5.4 | 確認済み/未確認の分類 | 🤖 | スペック項目ごとに「ページで確認済み」「要問い合わせ」を分類 |
| 5.5 | 質問テンプレート生成 | 🤖 | **未確認項目のみ**で工場別に中国語の質問文を生成 |
| 5.5 | 1688チャットで工場に問い合わせ | 👤 | テンプレートをコピペして送信 |
| 5.6 | チャットログをAIに共有 | 👤 | テキストコピペ or スクショ共有 |
| 5.7 | チャットログをNocoDB登録 | 🤖 | チャットログ解析で構造化→登録 |
| 5.8 | 工場回答でスペック評価を更新 | 🤖 | 回答内容でスペックスコアを付与・更新 |
| 5.9 | 工場回答の比較表作成 | 🤖 | 全工場の回答をスペック項目×工場のマトリクスで整理 |
| 5.10 | 追加質問の提案 | 🤖 | 未回答・曖昧な回答がある項目を特定、追加質問を生成 |
