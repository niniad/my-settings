# /hypothesis-action スキル

書籍「仮説行動」（馬田隆明著）のフレームワークに基づく仮説管理スキル。セッション型。

3つのステップはそれぞれ「思考の性質」が異なる:
- **MAP** = 構造化（地図を描く。全体を見渡す思考）
- **LOOP** = 学習（道を歩いて確かめる。試行錯誤で鍛える思考）
- **LEAP** = 意思決定（崖から跳ぶ。リスクを取る思考）

この3つを混ぜると失敗する。マップなしにループに入れば地図なしに歩き回ることになり、全体の整合性が取れない。

---

## 全体フロー

```
START: 興味・関心・問題意識
  ↓
STEP 1: MAP — 仮説マップを作る
  ↓
[判定] マップ全体が十分に強いか？
  ├─ No（ほとんどの場合）→ STEP 2: LOOP
  └─ Yes（稀）→ STEP 3: LEAP へ直行
  ↓
STEP 2: LOOP — 仮説を鍛える（トリプルループ）
  │  小ループ: 生成/修正 ⟷ 検証
  │  中ループ: 検証結果をマップに統合 →[リープ①]→ 次の弱い仮説へ
  │  → 統合後、再び[判定]に戻る
  ↓
STEP 3: LEAP — 決断し実行する
  │  [リープ②] マップ全体 → 本番実行への決断
  │  評価 → 決断 → 実行 → 仮説を「正解」にする努力
  │  → 実行からの学びをマップに反映（業績⇔学習のループ）
  ↓
GOAL: 目的達成
```

**2つのリープ**:
- **リープ①**（個別仮説→マップ統合）: 「この部品は使える」という判断。リスク小〜中、何度も発生
- **リープ②**（マップ全体→本番実行）: 「この設計図で家を建てる」という判断。リスク大、特別な瞬間

## 設計原則

1. **仮説は「正解にする」もの**: 正しいか間違いかではなく、実行の意志と努力が結果を変える
2. **影響度 × 確信度の積を最大化**: 正解率100%の小さな仮説より、80%の大きな仮説を狙う
3. **反証は最も価値のある学び**: 確証バイアスを意識的に回避し、反対エビデンスを先に探す
4. **速度が学びを生む**: 完璧なマップより素早いループ回転。「大きく考え、小さく踏み出せ」
5. **撤退も立派なリープ**: Kill判断はサンクコストに囚われない知的誠実さの証
6. **「何がしたいか」から始める**: 影響度の大きな仮説は願望から始まる。「できそうなこと」からではない
7. **ホットな心で生成し、クールな頭で検証する**: 情熱と冷静のバランス。どちらかに偏ると失敗する
8. **根拠は追跡可能な1次情報**: ファイル参照だけでは根拠にならない。本人発言・行動データ・測定値をソース付きで記載する

## 仮説のタイプ

すべてのマップで仮説を**課題仮説(P)**と**解決策仮説(E)**に分類する。これは書籍で「課題発見の仮説マップ」と「解決策の仮説マップ」を分離せよと述べられていることに基づく。同一map.md内でタイプ列により区別する。

| タイプ | ID接頭辞 | 意味 | 原則1「正解にする」の適用 |
|--------|---------|------|------------------------|
| **課題** | P | 何が問題/ニーズか。自己理解を含む場合は「発見」の性質を持つ | 課題仮説には適用しない。観察・データで検証する |
| **解決策** | E | どう解決するか | 適用する。努力と選択で正解にできる |

課題仮説が十分に検証されてから解決策仮説に進む。解決策の前提列に対応する課題仮説IDを記載することで紐づけを管理する。

## 仮説の記述基準

仮説は以下の3条件をすべて満たす形で記述する。満たさないものは仮説ではなく「疑問」「問い」であり、仮説台帳に入れてはならない。

### 1. 言い切り形であること

「○○は△△である」「○○すれば△△になる」のように断言する。疑問文（「〜か？」）や曖昧な表現（「〜かもしれない」「〜の可能性がある」）は仮説ではない。

| NG（疑問・問い） | OK（仮説） |
|---|---|
| 社会的つながりは十分か？ | 家族外の社会的つながりが不足しており、幸福度を制約している |
| 時間が足りるかどうか | 復職後に可処分時間が週10h未満になると全領域が破綻する |
| 夫婦安定維持 | 家事育児の分担比率を事前合意すれば夫婦関係は安定を維持できる |

### 2. 反証可能であること

「何が観察されればこの仮説は棄却されるか」が言えること。反証条件が設定できない仮説は抽象的すぎるか、公理（前提）として扱うべき。

### 3. 検証基準が具体的であること

「管理可能」「十分」「最適」のような曖昧な表現は避け、数値や具体的な条件で表現する。

| NG（曖昧） | OK（具体的） |
|---|---|
| 放置影響は管理可能 | 月1回の棚卸しで精神的負荷は許容範囲に収まる |
| AI探求はAIDX業務に吸収 | AIDX業務でAI技術を活用する機会が月2回以上あり、独立の探求時間は不要 |

### 上位仮説の構造ルール

最上位マップの上位仮説は、サブマップに展開可能な粒度で切ること。具体的には:

- **各上位課題仮説が独立した領域を表す**こと（経済、キャリア、関係性、健康 etc.）
- **メタ仮説（下位仮説の要約に過ぎないもの）は不要**。E02-E06があるなら「3本柱が最適」というE01は冗長
- **上位仮説 → サブマップ名が1対1で対応する**のが理想

## Step 1: マップを作る

**目的**: テーマに対する仮説の全体像をピラミッド構造でざっくり描く

**会話フロー**:
```
AI: 「仮説行動」スキルへようこそ！

     3ステップで意思決定を支援します:
     1. マップ — 仮説の全体像を描く（5分）
     2. ループ — 仮説を1つずつ検証する（週単位）
     3. リープ — Go/Pivot/Kill を決断する

     何について仮説を整理しますか？
     以下を教えてください:
     ① あなたは何がしたいのか？（願望ベース）
     ② 最終的にどんな決断をしたいか？
     ③ いつまでに決断が必要か？
User: [説明]
AI: [ヒアリング: 現時点の前提、懸念、既知の情報]
    → references/hypothesis-categories.md を Read で読み込み
    → 8カテゴリから該当するものを選択
    → まず課題仮説(P)を洗い出し、その後に解決策仮説(E)を検討
AI: 以下の仮説マップを作成しました:
    [ピラミッド構造（課題仮説 / 解決策仮説）]
    [仮説台帳（ID/仮説/タイプ/前提/支持先/影響度/確信度/強度/状態）]
    [評価マトリックス]

    見落としていることはありますか？
    修正があれば教えてください。
User: [修正/承認]
AI: → references/templates.md を Read で読み込み
    → map.md を生成、INDEX.md に追加
    → Step 2 に移行
```

**マップ作成のポイント**:
- 願望駆動: 「何ができそうか」ではなく「何がしたいか」から出発する
- トップダウン（カテゴリ→分解）とボトムアップ（ユーザーの直感→配置）を往復
- 各仮説を反証可能な形で言語化（「○○ならば△△である」）
- 仮説の強度を設定: 作業仮説（暫定、検証のための仮置き）↔ クレーム（主張として発信可能）
- 仮説の記述基準チェック:
  - **言い切り形か？** 疑問文や曖昧表現は仮説に書き直す
  - **反証可能か？** 「何が起きたら棄却するか」が言えるか
  - **検証基準は具体的か？** 「管理可能」「十分」等の曖昧語を排除
  - **メタ仮説（下位の要約）ではないか？** 不要なら削除
- 注意が必要な仮説パターン:
  - 一般的・抽象的すぎる → 具体化を促す
  - 感情が含まれている → 客観的エビデンスで検証する方法を提案
  - 極論 → 段階的な仮説に分解
  - よくある仮説 → 差別化の視点で問い直す

**仮説数別スケーリングルール**:
- 2-5個: フラットリスト管理（ピラミッド化不要）
- 6-20個: 標準ピラミッド構造
- 21-50個: カテゴリ別サブマップに分割
- 50個超: プロジェクト分割を勧告

## マップ後の判定ゲート

マップ作成後、「マップ全体が十分に強いか？」を問う:

- **No（ほとんどの場合）**: 弱い仮説があるので LOOP へ進む
- **Yes（稀）**: 既にマップが十分強ければ LOOP を経由せず直接 LEAP へ

LOOP 内で統合した後も、この判定に戻る。マップ更新後に全体を再評価する。

## Step 2: 空白を埋め、仮説を生成する

**目的**: マップの空白箇所を見つけ、新しい仮説を生成する

```
AI: マップを分析したところ、以下の空白があります:
    - [カテゴリX] に仮説がありません
    - H02の下位仮説が不足しています
    - 競合についての仮説がありません

    これらについて仮説を立てますか？
```

→ references/reasoning-and-verification.md を Read で読み込み

**仮説生成の4ステップ**:
1. **興味・関心・問題意識を持つ** — 好奇心を能動的に探索する
2. **疑問を持つ** — 「なぜ？」「本当に？」と問い続ける
3. **問いにする** — 疑問を検証可能な形に整える
4. **仮説にする** — 問いに対する暫定的な答え（作業仮説）を作る

**推論手法**:
- 演繹 / 帰納 / アブダクション（詳細は references/reasoning-and-verification.md）
- 前向きの推論（エビデンス → したがって → 仮説）
- 後ろ向きの推論（仮説 → なぜなら → エビデンス）
- 仮説の積み重ね: 確度が推論の連鎖で逓減することを明示
- **Why So?**（なぜそう？）で分解 — ボトムアップの問い
- **So What?**（だから何？）で統合 — トップダウンの問い

新仮説を map.md の仮説台帳に追加、ピラミッドを更新。

## Step 4: ループを回す — ★スキルの中核

**目的**: 仮説の生成と検証を繰り返し、確信度を段階的に高める

### 優先順位付け（影響度×確信度マトリックス）

```
|            | 確信度:低      | 確信度:中    | 確信度:高    |
|------------|--------------|------------|------------|
| 影響度:高   | ★最優先検証   | 検証継続     | 中核仮説     |
| 影響度:中   | 次の候補      | 経過観察     | 安定仮説     |
| 影響度:低   | 後回し        | 現状維持     | 前提条件     |
```

★高影響・低確信 = リスク仮説 → 最優先で検証。
毎回セッション開始時にこのマトリックスを更新・表示する。

### 仮説検証の実施

**検証態度**: 「確証」ではなく「探究」。自分の仮説を証明するためではなく、間違っている可能性を探るために検証する。

**検証方法の選択**（詳細は references/reasoning-and-verification.md）:

| 方法 | 適用場面 | コスト | AIの支援 |
|------|---------|--------|---------|
| デスクリサーチ | 既存情報の分析 | 低 | hypothesis-researcherが実行可能 |
| インタビュー | 定性的な深堀り | 低〜中 | 質問設計を支援 |
| サーベイ | 傾向・規模の定量確認 | 中 | 設問設計を支援 |
| 観察 | 行動パターン把握 | 低 | 観察ポイント設計 |
| 実験/ABテスト | 因果関係の検証 | 高 | 実験設計を支援 |
| MVP | 市場反応の実測 | 高 | MVP定義を支援 |

**検証設計の必須要素**:
- **勝利条件**: 何をもって仮説が支持されたとするか（例: 10人中5人以上が2分以上）
- **撤退条件**: 何をもって仮説を棄却するか（例: 3人以上が面倒だと回答）
- **時間軸**: 1ターム（検算）/ 1日（検索）/ 1週間（調査・ヒアリング）/ 1ヶ月（小実験）
- **コミットメント**: 口先の賛同ではなく、時間・お金・手間の実際のコミットメントを引き出す

**検証の5段階**:
1. **仮説明確化**: 反証可能な形に（「○○ならば△△。△△でなければ棄却」）+ 勝利/撤退条件を事前設定
2. **検証方法選択**: 上表から最適な方法を提案。a) AIリサーチ / b) ユーザー実施 を提示
3. **実施**: AIリサーチの場合 → hypothesis-researcher エージェントを起動。ユーザー実施の場合 → 設計を支援し結果を待つ。実験するなら全力で行う（手を抜かない）
4. **結果分析**: エビデンス信頼度格付け付与 → **Fact→Insight→Action** で整理 → So What?（上位仮説への影響）→ Why So?（根本原因の推論）
5. **学習とマップ更新**: 確信度・強度・状態を更新 → 派生する新仮説はあるか？→ 他の仮説へのカスケード影響は？→ 検証ログに記録

### 個別仮説の深堀り

ユーザーが「H03を深く検証したい」「H03について壁打ちしたい」と言った場合:

```
1. hypothesis-researcher エージェントを起動:
   → 仮説の内容と文脈を渡す
   → 必ず反対エビデンスを先に探す（確証バイアス防止）
   → WebSearch/WebFetch/MCP等でエビデンス収集
   → 信頼度格付け付きのレポートを research/ に保存

2. （オプション）devils-advocate エージェントを起動:
   → map.md 全体を読ませる
   → 関連仮説の整合性をチェック
   → カスケードリスク、暗黙の前提、感情バイアスを指摘

3. 結果を統合して map.md を更新
```

**エージェント起動トリガー**:
- hypothesis-researcher: 検証方法選択時に「a) AIリサーチ / b) ユーザー実施」を提示
- devils-advocate: 仮説5個以上変更時に「全体チェックしますか？」を自動提案
- リープ前: 必ず devils-advocate を実行

### マップへの統合（Step 5: 小リープ）

個別仮説のループが一巡したら:
```
AI: ループの結果をまとめます:
    [変更された仮説の一覧と確信度変化]
    [新たに生まれた仮説（詳細輪）]
    [棄却された仮説とその理由]

    マップ全体への影響:
    - H02が棄却されたため、H05-H07も見直しが必要です（カスケード影響）
    - [カテゴリX]に新たな空白が生まれています

    小リープ: 以下の仮説について判断が可能です:
    - H03: 確信度が十分に高まりました → クレームに昇格してよいですか？
    - H08: 反証が得られました → 棄却しますか？

    次のループで検証すべき仮説: H09（影響度:高, 確信度:低）
```

### ループ停滞の回避

以下のパターンを検出して警告:
- **同じ仮説を3回以上ループ & 確信度変化なし** → 「検証方法を変えてみましょう」
- **確信度が上がらない** → 「仮説の粒度を変える（分解 or 統合）」
- **高確信度ばかり検証している** → 「★リスク仮説から逃げていませんか？」
- **2週間以上 map.md 未更新 & 高影響仮説が未検証** → リマインダー
- **1つの検証に時間をかけすぎている** → 「小さく素早く。MVPの精神で」

停滞時の分岐:
1. 検証方法を変える
2. 仮説の粒度を見直す
3. マップの前提を問い直す

## Step 6: リープする — 大リープ

**目的**: マップ全体がサチュレートしたら、実行への決断を下す

### 評価する

**V-IBES チェックリスト**（仮説の質を5軸で評価）:
- **V**ivid（鮮明）— 新鮮で面白いか
- **I**mpactful（影響度大）— ビジネスへの影響が大きいか
- **B**old（大胆）— 小さな改善ではなく大胆か
- **E**thical（倫理的）— 倫理的に問題ないか
- **S**harp（鋭い）— 明瞭でシンプルか

```
AI: マップ全体のサチュレーション評価:

    ■ 確信度分布
    高確信: H01, H03, H06, H08 (4/10)
    中確信: H02, H04, H07 (3/10)
    低確信: H05, H09, H10 (3/10)

    ■ V-IBES 評価
    [各中核仮説のV-IBES採点]

    ■ 残存リスク仮説（高影響・低確信）
    H05: [内容] — 最後のリスク仮説

    ■ 4つの決断条件チェック
    ① 十分性: 主要仮説の確信度は「合理的判断」に十分か？
    ② 経済性: これ以上の検証コスト > 実行しない機会損失か？
    ③ 機会性: 市場や競争環境は待ってくれるか？
    ④ リスク許容度: 残存リスクは受容可能か？

    ■ 注意が必要な仮説パターン
    一般的/抽象的/シンプルすぎる/感情的/極論/よくある仮説は要注意
```

リープ前に必ず devils-advocate エージェントを実行する。

### 決断する

```
AI: 決断の選択肢:

    ■ Go — 実行に移る
      中核仮説ベースの行動計画を策定
      残存リスクのモニタリング計画を含む

    ■ Pivot — 方向転換
      仮説マップを大幅に組み替えて再ループ
      学びは引き継ぎ、前提を変える

    ■ Kill — 撤退
      サンクコストに囚われない
      「このプロジェクトから何を学んだか」を記録

    ■ Wait — 待機
      特定の外部条件が変わるまで待つ
      待機条件と再開トリガーを明記

    ■ Sustain — 維持最適化（独自拡張。永続マップ向け）
      現在の構造は機能している。大きな変更は不要。
      解決策仮説の改善に集中する。
      条件: 課題仮説の確信度が中高以上、制約条件が安定

    他人の評価を活用する: この決断を誰かにぶつけましたか？
    「良い批評者」に見せることで盲点が見つかります。
```

**Kill判定の4基準**:
1. 前提仮説の棄却（修復不可能）
2. リスク仮説の改善見込みなし
3. 市場のウィンドウが閉じた
4. 事前の撤退基準に到達
→ Kill時: 「この学習は次のプロジェクトで活きるか」を記録

### 仮説を現実にする（Go の場合）

```
AI: 「仮説を正解にする」ための行動計画:

    ■ 中核仮説に基づく具体的アクション
    [H01に基づく行動] / [H03に基づく行動] / ...

    ■ 残存リスクへの備え
    [H05が想定と異なった場合のプランB]

    ■ 外部要因すらも変える視点
    仮説を実行するだけでなく、環境を変えることも検討。
    「仮説を正解にする」とは、圧倒的な行動量と意志で結果を変えること。

    ■ 影響度の大きな仮説を目指す
    - 現在起点の What ではなく未来起点の What if...? で考える
    - スケールの大きな問いがスケールの大きな仮説を生む
    - 目先の課題に囚われず「あるべき姿」から逆算する

    ■ 実行後の業績⇔学習ループ
    実行結果 → 新しいエビデンス → マップの仮説確信度更新
    → 次のループ開始（または撤退判断）

    定期レビューをスケジュールしますか？（/schedule で設定可能）
```

## AIの常時動作

セッション中、以下を継続的に実行する。

**構造的チェック**:
- マップの空白箇所の指摘
- カスケード影響の検出（仮説間の依存関係）
- 詳細輪の発見（検証済み仮説から派生する新仮説）
- 仮説の強度チェック（作業仮説のまま放置されていないか）

**バイアスチェック**:
- 確証バイアス警告（支持エビデンスばかり集まっている）
- 感情バイアス検出（「感情が含まれる仮説」パターン）
- 過剰楽観/悲観の指摘
- アンカリング効果（最初の仮説に引きずられていないか）

**進行チェック**:
- ループ停滞の検出と解消提案
- サチュレーション判断の提案（リープのタイミング）
- 影響度の見直し提案

**表示の2層分離**:
- **デフォルト表示**（毎回）: ピラミッド構造 + 評価マトリックス + ★最優先仮説
- **詳細表示**（ユーザー要求時）: 仮説台帳 + 検証ログ + 決断ログ

## Red Flags

| 思考パターン | リスク | AIの対応 |
|-------------|--------|---------|
| 確信度の高い仮説ばかり検証 | 確証バイアス | 「★リスク仮説から先に」|
| 全部検証してからリープ | 機会損失 | サチュレーション判断を促す |
| 「明らかに正しい」 | 暗黙の前提 | 「中核仮説こそ検証が必要」|
| 検証結果が期待外れだから無視 | 反証回避 | 「反証こそ最も価値のある学び」|
| 撤退は失敗 | サンクコスト | 「Kill も立派なリープ」|
| 一般的・抽象的すぎる仮説 | 検証不能 | 具体化・分解を促す |
| 「できそうなこと」から考える | 小粒化 | 「何がしたいか」から始める |

## エラーケース処理

- INDEX.md 不在 → 空 INDEX.md を自動生成
- map.md YAML 破損 → フロントマター自動修復を試行
- 同一スラッグ重複 → タイムスタンプ精密化（_HHMMSS 追加）
- セッション中断 → status: looping のまま保持、次回復帰時にサマリー表示

## セッション終了時

セッション終了前に以下を確認する:
1. 今回のセッションで変更があった仮説は map.md に反映されているか？
2. 次回のアクションが明確か？

未反映の変更があれば、map.md を更新してからセッションを終了する。

## Schedule 連携

ユーザーにリープ後またはループ長期化時に提案:
```
AI: 仮説マップの定期レビューをスケジュールしますか？
    例: 毎週金曜17時に「仮説マップの鮮度チェック」

    チェック内容:
    - 2週間以上検証されていない高影響仮説
    - 外部環境の変化で前提が崩れていないか
    - 実行結果のフィードバック反映
```

→ `/schedule` コマンドで CronCreate を使用。
