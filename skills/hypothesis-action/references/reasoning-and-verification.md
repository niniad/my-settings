## 推論方法

### 演繹（Deduction）

既知の前提から論理的に結論を導く。前提が正しければ結論は必ず正しい。
- 例: 「この市場の全プレイヤーは価格競争に陥っている」+「我々はこの市場に参入する」→「我々も価格競争に直面する」
- 強み: 論理的に確実。弱み: 前提の正しさに依存する。

### 帰納（Induction）

個別の観察から一般的な法則を推定する。確率的な結論。
- 例: 「インタビューした10社中8社が同じ課題を挙げた」→「この業界の企業の多くが同じ課題を抱えている可能性が高い」
- 強み: 現実のデータに基づく。弱み: サンプルの偏りに影響される。

### アブダクション（Abduction）

観察された事象から最も合理的な説明を推定する。仮説生成に最も適した推論。
- 例: 「競合A社が突然値下げした」→「A社は新規参入者への対抗策を打っている可能性がある」
- 強み: 仮説を素早く生成できる。弱み: 最もらしいが正しいとは限らない。

### 前向きの推論と後ろ向きの推論

- **前向き**: エビデンス → したがって → 仮説（データから仮説を組み立てる）
- **後ろ向き**: 仮説 → なぜなら → エビデンス（仮説から必要なエビデンスを逆算する）

検証設計には後ろ向きの推論が有効。「この仮説が正しいなら、何が観察されるはずか？」

### OODAループの適用

仮説生成における思考の回転を加速する枠組み:
- **Observe（観察）**: 生データ・一次情報を偏りなく集める
- **Orient（情勢判断）**: 観察結果を既存の知識・文脈と統合し、意味を読み取る
- **Decide（意思決定）**: 複数の仮説候補から検証すべきものを選択する
- **Act（行動）**: 検証を実行し、結果を次のObserveに還流する

### 仮説の積み重ねと確度逓減

推論を連鎖させるほど、全体の確度は逓減する:
- 仮説A（確度80%）→ Aを前提とする仮説B（確度70%）→ A∧Bの確度は56%
- 3段階の推論連鎖では確度が大幅に下がることを常に意識する
- 連鎖が長い仮説ほど、途中の前提を個別に検証する必要がある

## 検証方法

### 6種類の検証方法と使い分け

| 方法 | 適用場面 | コスト | 確度向上 | AI支援 |
|------|---------|--------|---------|--------|
| デスクリサーチ | 既存情報・データの分析 | 低 | 中 | 直接実行可能 |
| インタビュー | 定性的な深堀り・動機の理解 | 低〜中 | 高 | 質問設計を支援 |
| サーベイ | 傾向・規模の定量確認 | 中 | 中〜高 | 設問設計を支援 |
| 観察 | 実際の行動パターン把握 | 低 | 高 | 観察ポイント設計 |
| 実験/ABテスト | 因果関係の検証 | 高 | 非常に高 | 実験設計を支援 |
| MVP | 市場反応の実測 | 高 | 非常に高 | MVP定義を支援 |

**選択の指針**: まずデスクリサーチで既知情報を整理し、不足をインタビュー/サーベイで補い、重要な仮説は実験/MVPで確定させる。コストの低い方法から段階的に進める。

### 検証の5段階手順

1. **仮説明確化**: 反証可能な形に言語化する（「○○ならば△△。△△でなければ棄却」）
2. **検証方法選択**: コスト・期間・確度向上のバランスで最適な方法を選ぶ
3. **実施**: AIが直接リサーチ可能な場合はエージェントを起動。ユーザー実施の場合は設計を支援
4. **結果分析**: エビデンス格付け + So What? / Why So? の双方向分析
5. **学習とマップ更新**: 確信度・強度・状態を更新し、カスケード影響をチェック

## 検証設計

### 勝利条件と撤退条件の事前設定

検証に入る前に、必ず以下を明確にする:
- **勝利条件**: 何をもって仮説が支持されたとするか
  - 例: 「10人中5人以上が2分以上かけていれば勝利」
- **撤退条件**: 何をもって仮説を棄却するか
  - 例: 「3人以上が面倒だと回答すれば撤退」
- **その後の行動**: 勝利時と撤退時にそれぞれ何をするか

曖昧なまま検証に入ると、結果をどう解釈すべきか分からなくなる。基準を決めるにはドメイン知識が必要であり、類似事例のベンチマークを参考にする。

### 検証の時間軸設計

検証方法を時間軸で整理することで、素早く検証できるものから着手できる:
- **1ターム**: 検算、具体的な議論への活用
- **1日**: 検索手段の時間軸を意識した調査
- **1週間**: 机上での調査、ヒアリング
- **1ヶ月**: 小実験

コストの低い方法から段階的に進め、重要な仮説ほど高コストの検証（実験/MVP）で確定させる。

### 結果の整理フォーマット: Fact → Insight → Action

検証結果は以下の3層で整理する:
- **Fact**: 観察された事実（データ、発言、行動）
- **Insight**: 事実から得られた洞察（So What? / Why So?）
- **Action**: 洞察に基づく次の行動

## 検証態度

### 反証可能性の重視

- 検証できない仮説は仮説ではない。「○○かもしれない」を「○○ならば△△が観察される」に変換する
- 反証条件を事前に明記: 「何が起きたらこの仮説を棄却するか」

### 確証バイアスの回避

- 仮説を支持するエビデンスだけを集めがちな認知傾向を意識する
- **反対エビデンスを先に探す**: 検証の際は「この仮説が間違っている証拠」から収集する
- 「都合の良いデータだけ見ていないか？」を定期的にセルフチェック

### So What? / Why So? の双方向分析

- **So What?**（だから何？）: 検証結果が上位仮説やマップ全体にどう影響するかを問う
- **Why So?**（なぜそうなのか？）: 結果の根本原因を掘り下げ、新たな仮説の種を見つける
- 両方向を行き来することで、表面的な分析を避ける

## エビデンス信頼度格付け

### ソース等級（信頼性）

| 等級 | 定義 | 例 |
|------|------|-----|
| A | 公式統計・査読論文・一次データ | 政府統計、学術論文、自社実験データ |
| B | 信頼性の高い二次情報 | 大手調査会社レポート、業界団体発表 |
| C | 一般的なメディア・識者意見 | 経済紙記事、専門家インタビュー |
| D | 非公式情報・限定的なサンプル | ブログ記事、SNS投稿、少数事例 |
| E | 未検証・伝聞・推測 | 噂、個人的印象、裏取りなしの情報 |

### 確信度（検証の厚み）

| レベル | 定義 | 判断基準 |
|--------|------|---------|
| 1 | 非常に高い | 複数の独立ソース（等級A-B）で確認済み |
| 2 | 高い | 信頼できるソースで確認、反証なし |
| 3 | 中程度 | 一定のエビデンスあり、反証も一部あり |
| 4 | 低い | 限定的なエビデンスのみ、未確認事項が多い |
| 5 | 非常に低い | 反証あり、または根拠が推測のみ |

## 仮説の強度グラデーション

仮説は検証の進展に応じて強度が変化する。4段階で管理する。

### 作業仮説（Working Hypothesis）

- **定義**: 検証のために暫定的に置いた仮説。正しいとも間違っているとも判断していない
- **用途**: 検証の出発点。「もし○○だとしたら」の仮置き
- **昇格基準**: 初期エビデンスが得られ、方向性が見えてきたとき → 仮説へ

### 仮説（Hypothesis）

- **定義**: 一定のエビデンスに基づき、検証を進めている段階の仮説
- **用途**: ループの中核。検証を通じて確信度を上げ下げする
- **昇格基準**: 複数ソースで裏付けられ、反証が見つからないとき → 強い仮説へ
- **降格基準**: 反証が見つかった、または前提が崩れたとき → 作業仮説へ差し戻し or 棄却

### 強い仮説（Strong Hypothesis）

- **定義**: 十分なエビデンスに裏付けられ、意思決定の基盤として信頼できる仮説
- **用途**: リープ判断の中核。行動計画の前提として採用する
- **昇格基準**: 反証テストに耐え、他者への説明でも説得力があるとき → クレームへ
- **降格基準**: 新たな反証が出現した、環境変化で前提が変わったとき → 仮説へ

### クレーム（Claim）

- **定義**: 外部に主張として発信できるレベルの確信を持つ仮説。事実上の「結論」
- **用途**: プレゼン、提案書、事業計画の根拠として使用
- **降格基準**: 重大な反証が出現したとき → 強い仮説へ差し戻し
- **注意**: クレームであっても「暫定的な結論」であり、新しいエビデンスで覆る可能性は常にある

## V-IBES 仮説評価チェックリスト

リープ前に仮説の質を5軸で評価する。良い仮説かどうかを柔軟に判断するためのフレームワーク。

| 軸 | 意味 | 評価の問い |
|---|------|---------|
| **V**ivid（鮮明） | 新鮮で面白いか | この仮説は独自の視点を含んでいるか？誰もが思いつくものではないか？ |
| **I**mpactful（影響度大） | ビジネスへの影響が大きいか | この仮説が正しければ、事業に大きな影響を与えるか？ |
| **B**old（大胆） | 小さな改善ではなく大胆か | 安全な仮説に逃げていないか？大胆に考えているか？ |
| **E**thical（倫理的） | 倫理的に問題ないか | 長期にわたって社会的に受け入れられるか？ |
| **S**harp（鋭い） | 明瞭でシンプルか | 仮説は明瞭でシンプルに表現されているか？ |

### 注意が必要な仮説パターン

以下の仮説は一見良さそうに見えるが、実際には質が低い可能性がある:
- 一般的 / 抽象的 / シンプルすぎる / 分かりやすすぎる仮説
- 感情が含まれる仮説
- 極論である仮説
- よくある仮説

確信度を過大評価して見えづらい評価軸を過小評価しがち。直感（門番）の評価は手軽で速いがミスも多い。分析的評価（城壁）は時間がかかるが精度が高い。

## リスク対処

### リスクの本質

本当の賢さは「リスクを避ける」ことではなく、「目的を達成するために適切なリスクを取る」こと。

- **ダウンサイドリスクの緩和**: 知識やスキルで失敗の幅を小さくする
- **アップサイドの最大化**: 利益を得られるか不明な「機会を逃すリスク」にも注意
- リスクの定義 = 確率 × 影響。目的のためにリスクの定義を行い、その目的を達成するために適切なリスクを取る

## エビデンスの1次情報要件

仮説マップの根拠は、追跡可能な1次情報を優先する。学術エビデンスは理論的裏付けとして付記するが、間接参照だけでは根拠にならない。

**根拠欄の記載ルール**:
- 本人発言: (lifeセッションN Q回答 YYYY-MM-DD)
- 行動データ: (Apple Health / Chrome / Steam等)
- プロフィール: (profile.json ドメインID source_grade級)
- 学術: (著者(年) 概要, 学術A-E級) — あくまで付記
