# /setup-optimizer v3 — 原理ベース設計

テンプレートを当てはめるのではなく、**各要素を入れる理由を説明できること**を設計原則とする。

---

## 判断基準（Tier区分）

### Tier 1: 技術的事実（必ず適用）

| 要素 | 根拠 | 格付け |
|------|------|--------|
| auto-compact閾値をデフォルト(83.5%)より下げる | デフォルトではバッファ不足でcompaction失敗リスク | [B-1] |
| CLAUDE.mdにコンパクション後の復帰手順を記載 | compaction後にClaudeが文脈を失う | [B-1] |
| 不要なツール定義を減らす | 50ツール×1.5K = 75Kトークン消費 | [B-1] |
| CLAUDE.mdは100行以内 | 毎セッション全文ロード。短いほどトークン効率が高い | [B-1] |
| CLAUDE.mdはインデックス+原則のみ。詳細手順はスキルやrules/に外出し | 詳細知識をConstitutional Layerに置くとトークン効率が悪い | [B-1] |
| グローバル設定と重複する記載をプロジェクトCLAUDE.mdに書かない | ~/.claude/CLAUDE.mdは毎セッション自動ロード済み | [A-1] |

### Tier 2: 有効な実践知（ヒアリングで必要と判断したら適用）

| 要素 | 根拠 | 格付け |
|------|------|--------|
| .claudeignore | バイナリ成果物(xlsx/pdf等)が検索ノイズになる | [C-2] |
| Notificationフック | 長セッションの入力待ち通知 — UX改善。品質への影響は間接的 | [C-2] |
| rules/session-guide.md | 行動を外部化し一貫性を高める。Claude Code公式機能 | [C-2] |
| ENABLE_TOOL_SEARCH | MCPが5個以上の場合にツール検索で85%削減 | [B-2] |
| サブエージェント構成 | 各エージェントは独立コンテキスト → 長いタスクの汚染防止 | [B-2] |

### Tier 3: 慣例（ユーザーが明示的に求めた場合のみ）

archive/, docs/, decisions.md, /statusコマンド, プロジェクト固有Agent, SessionStartフック

**エビデンスが弱く、プロジェクトによっては不要なため自動適用しない。**

## モード判定

引数 `$ARGUMENTS`:
- `1` / `new` / 「新規」 → Mode 1
- `2` / `health` / 「診断」「ヘルスチェック」 → Mode 2
- `optimize` / 「最適化」「トークン削減」「コンテンツ整理」 → Mode 2 + コンテンツ最適化実行
- `3` / `update` / `monitor` → Mode 3
- 引数なし → 3つの選択肢を提示

---

## Mode 1: 新規プロジェクト作成

### Phase 1: オープンヒアリング（1メッセージ）

カテゴリを選ばせない。ユーザーの言葉で説明させる。

```
新プロジェクトを作成します。

1. プロジェクト名（フォルダ名）:
2. 何をするプロジェクトか（自由記述）:
3. 主な成果物は何か:
4. 1セッションの目安: 短（〜30分）/ 中（〜2時間）/ 長（2時間以上）
5. 関連する既存プロジェクトがあれば:
```

### Phase 2: 収束（最大2往復）

Phase 1の回答を読んで判断する:

1. **重複チェック**: 回答5があれば `~/projects/[関連]/CLAUDE.md` 冒頭30行を読む。目的が類似していれば「既存プロジェクトに統合すべきでは？」と提案してMode 1を中止
2. **不明な点のみ追加質問**: 構成が一意に決まらない場合のみ質問する（最大2往復）
3. **推測の明示**: 推測した内容は構成提案に `[推測]` と明記する

### Phase 3: 構成提案

```
以下の構成を提案します。根拠を [] で付記しています。

📁 ~/projects/[名前]/
├── CLAUDE.md        ← [Tier 1] コンテキスト復元 + プロジェクト定義
├── tmp/             ← [Tier 1] 一時ファイル（グローバル設定で指定済み）
├── .gitignore       ← [ヒアリングから判断 / 推測]
├── [成果物フォルダ] ← [ヒアリング回答3から導出]
└── .claude/
    ├── settings.json ← [Tier 1] auto-compact 70%閾値
    [├── .claudeignore]  ← [Tier 2: バイナリ成果物がある場合のみ]
    [└── rules/]         ← [Tier 2: 長期・複数セッションの場合のみ]

含めない要素と理由:
  - [Tier 3要素]: [このプロジェクトでは不要と判断した理由]

変更・追加したい点はありますか？
```

### Phase 4: 生成

承認後にファイルを作成する。

**CLAUDE.md（必須構造・50〜80行を目標）**:
```markdown
# [プロジェクト名]

## コンパクション後の復帰手順
コンパクション直後は必ず:
1. この CLAUDE.md を再読
2. [ヒアリングから導出したプロジェクト固有の復元アクション]

## 目的
[ヒアリング回答2〜3から簡潔に記述]

## [ヒアリングで必要と判断したセクションのみ追加・最大3セクション]
```

**CLAUDE.mdの設計原則**:
- 詳細な手順や判断基準はスキルや rules/ に外出しし、CLAUDE.md にはポインタ（「→ /[スキル名] を参照」）のみ記載する
- ~/.claude/CLAUDE.md に記載済みの内容（日本語応答、tmp/使用、Windowsパス規約、encoding注意）はここに書かない

**settings.json（必須）**:
```json
{
  "env": {
    "CLAUDE_AUTOCOMPACT_PCT_OVERRIDE": "70"
  }
}
```

Tier 2として条件付き追加:
- `"ENABLE_TOOL_SEARCH": "auto:10"` — MCPが5個以上の場合
- `hooks.Notification` — Windowsで長セッションの場合（PowerShell MessageBox）

### Phase 5: 育成サイクルの案内

ファイル生成後、以下をユーザーに伝える:

```
プロジェクトの初期構成が完成しました。

📌 育成サイクルの目安:
  2〜3週間の運用後に `/setup-optimizer 2` を実行してください。
  蓄積されたメモリの棚卸しと、CLAUDE.mdの調整提案を行います。
```

## Mode 2: ヘルスチェック

### クロスプロジェクト分析（最初に実行）

`~/projects/` の全プロジェクトのCLAUDE.md冒頭30行を読む。詳細確認が必要なペアのみ全文読み込む（コンテキスト効率のため）。

検出対象:
- **重複プロジェクト**: 目的が重複するペア → 統合を提案
- **肥大化**: CLAUDE.md 150行超 → 分割を提案
- **非アクティブ**: 30日以上変更なし → アーカイブを提案

### Tier別チェック項目

**Tier 1（必ず実行）**:

| # | チェック | 基準 | Auto-fix |
|---|---------|------|----------|
| 1 | CLAUDE.md行数 | <100行 | 分割提案 |
| 2 | コンパクション復帰手順 | 存在すること | 追加可 |
| 3 | auto-compact設定 | 存在すること | 追加可 |
| 4 | グローバル設定との重複 | 重複なし | 指摘のみ |

**Tier 2（プロジェクト特性に応じて実行）**:

| # | チェック | 条件 | Auto-fix |
|---|---------|------|----------|
| 5 | .claudeignore | バイナリ成果物がある場合 | 生成可 |
| 6 | Hooks設定 | 長セッション運用の場合 | 提案のみ |
| 7 | ENABLE_TOOL_SEARCH | MCP5個超の場合 | 追加可 |
| 8 | rules/ | 複数セッション運用の場合 | 提案のみ |
| 9 | CLAUDE.mdインデックス化 | 詳細手順が直接記載されている場合 | スキル/rules/への外出し提案 |
| 10 | メモリ健全性 | auto-memoryが有効な場合 | 後述の手順で診断 |

**クロスプロジェクト**:

| # | チェック | Auto-fix |
|---|---------|----------|
| 11 | 重複プロジェクト | 統合提案 |
| 12 | 150行超CLAUDE.md | 分割提案 |
| 13 | 30日以上非アクティブ | アーカイブ提案 |

### 診断レポート形式

```
========================================
ヘルスチェックレポート [date]
========================================

🔴 要対応: [問題項目]
🟡 確認推奨: [注意項目]
✅ 問題なし: [正常項目]

---
クロスプロジェクト分析:
  [重複/肥大化/非アクティブの検出結果]
---

自動修正できる項目:
  [a] [項目] → [修正内容]

修正を実行しますか？ [a=すべて / b=選択 / c=レポートのみ]
```

### メモリ健全性チェック（Tier 2 #10: auto-memoryが有効な場合）

対象ディレクトリ: `~/.claude/projects/[プロジェクトスコープ]/memory/`

1. **MEMORY.md を読む** — インデックスの肥大化（200行超）を確認
2. **メモリファイル一覧を取得** — 総ファイル数を把握
3. **以下を検出してレポートに含める**:
   - **重複**: 類似の description を持つファイル → マージ提案
   - **陳腐化**: 内容がコードや設定の現状と乖離 → 更新または削除提案
   - **結晶化候補**: 同じテーマの feedback/project メモリが3件以上 → 「スキルや rules/ への構造化を検討してください」と提案（実行はユーザーが別セッションで行う）

**注意**: 結晶化の実行はこのスキルの責務外。「気づかせる」だけに留める。

---

### コンテンツ最適化手順（`optimize` 引数時 または Mode 2で行数80行超の場合）

**評価原則**: 「これを削除するとClaudeがミスをするか？しないなら削除する」

#### Step 1: コンテキスト収集

1. 対象CLAUDE.mdを全文読む
2. 参照されているスキルSKILL.mdを読む（`~/.claude/skills/*/SKILL.md`）
3. グローバルCLAUDE.md（`~/.claude/CLAUDE.md`）を読む

#### Step 2: 冗長性分析

各セクション・行について以下の3分類で評価:

| 分類 | 定義 | 対処 |
|------|------|------|
| **完全カット** | 他ファイルに同一内容が存在する / 行動指示がない哲学的記述 / システムが自動処理する | 削除 |
| **マージ** | 複数セクションが同じ目的を果たしている | 統合して1セクションに |
| **圧縮** | 同じ意味をより短く表現できる | 書き直し |

#### Step 3: 最適化プラン提示

```
CLAUDE.md最適化プラン
現在: XX行 → 目標: XX行（約XX%削減）

## 完全カット（他所に存在または効果なし）
| セクション | 理由 | 推定削減 |
|-----------|------|---------|
| [セクション名] | [根拠: どのファイルに存在するか/なぜ効果がないか] | ~XX tokens |

## マージ（重複を統合）
| 対象 | 方法 | 推定削減 |
|------|------|---------|
| [セクションA + B] | [統合後の構造] | ~XX tokens |

## 圧縮（同じ意味を短く）
| 対象 | 変更内容 | 推定削減 |
|------|---------|---------|
| [対象] | [具体的な圧縮方法] | ~XX tokens |

合計削減: ~XX tokens（XX%）

実行しますか？ [y=実行 / n=キャンセル / 修正=変更点を指定]
```

#### Step 4: 実行

承認後:
1. 最適化後のCLAUDE.mdを生成・上書き
2. 行数・トークン削減量を報告
3. **注意**: 削減後も「このセクションを削除してもClaudeはミスしないか？」を自問して確認する

## Mode 3: 更新モニター

```bash
claude --version
```

WebFetchまたはCHANGELOGで前回確認バージョンからの差分を確認する。

```
更新モニターレポート v[前回] → v[現在]
---
📌 設定に影響する可能性がある変更:
  [変更内容] → [影響する設定] → 移行推奨度: 高/中/低

🔄 陳腐化候補:
  [カスタム機能]: [ネイティブ機能で代替可能になった理由]

⚙️ PreCompact Issue #14160:
  [未解決: 現状維持 / 解決済み: 移行手順を提案]
```

承認後、該当するプロジェクトの settings.json / CLAUDE.md を更新する。

---

*設計原則: 各要素を入れる理由を説明できること。Tier 1は常に適用、Tier 2はヒアリングから推論、Tier 3は求められた場合のみ。*
