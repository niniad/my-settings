# /setup-optimizer v3 — 原理ベース設計

テンプレートを当てはめるのではなく、**各要素を入れる理由を説明できること**を設計原則とする。

---

## 判断基準（Tier区分）

### Tier 1: 技術的事実（必ず適用）

| 要素 | 根拠 | 格付け |
|------|------|--------|
| auto-compact閾値をデフォルト(83.5%)より下げる | デフォルトではバッファ不足でcompaction失敗リスク | [B-1] |
| CLAUDE.mdにコンパクション後の復帰手順を記載 | compaction後にClaudeが文脈を失う | [B-1] |
| 不要なツール定義を減らす | 50ツール×1.5K = 75Kトークン消費 | [B-1] |
| CLAUDE.mdは100行以内 | 毎セッション全文ロード。短いほどトークン効率が高い | [B-1] |
| グローバル設定と重複する記載をプロジェクトCLAUDE.mdに書かない | ~/.claude/CLAUDE.mdは毎セッション自動ロード済み | [A-1] |

### Tier 2: 有効な実践知（ヒアリングで必要と判断したら適用）

| 要素 | 根拠 | 格付け |
|------|------|--------|
| .claudeignore | バイナリ成果物(xlsx/pdf等)が検索ノイズになる | [C-2] |
| Notificationフック | 長セッションの入力待ち通知 — UX改善。品質への影響は間接的 | [C-2] |
| rules/session-guide.md | 行動を外部化し一貫性を高める。Claude Code公式機能 | [C-2] |
| ENABLE_TOOL_SEARCH | MCPが5個以上の場合にツール検索で85%削減 | [B-2] |
| サブエージェント構成 | 各エージェントは独立コンテキスト → 長いタスクの汚染防止 | [B-2] |

### Tier 3: 慣例（ユーザーが明示的に求めた場合のみ）

archive/, docs/, decisions.md, /statusコマンド, プロジェクト固有Agent, SessionStartフック

**エビデンスが弱く、プロジェクトによっては不要なため自動適用しない。**

## モード判定

引数 `$ARGUMENTS`:
- `1` / `new` / 「新規」 → Mode 1
- `2` / `health` / 「診断」「ヘルスチェック」 → Mode 2
- `3` / `update` / `monitor` → Mode 3
- 引数なし → 3つの選択肢を提示

---

## Mode 1: 新規プロジェクト作成

### Phase 1: オープンヒアリング（1メッセージ）

カテゴリを選ばせない。ユーザーの言葉で説明させる。

```
新プロジェクトを作成します。

1. プロジェクト名（フォルダ名）:
2. 何をするプロジェクトか（自由記述）:
3. 主な成果物は何か:
4. 1セッションの目安: 短（〜30分）/ 中（〜2時間）/ 長（2時間以上）
5. 関連する既存プロジェクトがあれば:
```

### Phase 2: 収束（最大2往復）

Phase 1の回答を読んで判断する:

1. **重複チェック**: 回答5があれば `~/projects/[関連]/CLAUDE.md` 冒頭30行を読む。目的が類似していれば「既存プロジェクトに統合すべきでは？」と提案してMode 1を中止
2. **不明な点のみ追加質問**: 構成が一意に決まらない場合のみ質問する（最大2往復）
3. **推測の明示**: 推測した内容は構成提案に `[推測]` と明記する

### Phase 3: 構成提案

```
以下の構成を提案します。根拠を [] で付記しています。

📁 ~/projects/[名前]/
├── CLAUDE.md        ← [Tier 1] コンテキスト復元 + プロジェクト定義
├── tmp/             ← [Tier 1] 一時ファイル（グローバル設定で指定済み）
├── .gitignore       ← [ヒアリングから判断 / 推測]
├── [成果物フォルダ] ← [ヒアリング回答3から導出]
└── .claude/
    ├── settings.json ← [Tier 1] auto-compact 70%閾値
    [├── .claudeignore]  ← [Tier 2: バイナリ成果物がある場合のみ]
    [└── rules/]         ← [Tier 2: 長期・複数セッションの場合のみ]

含めない要素と理由:
  - [Tier 3要素]: [このプロジェクトでは不要と判断した理由]

変更・追加したい点はありますか？
```

### Phase 4: 生成

承認後にファイルを作成する。

**CLAUDE.md（必須構造・50〜80行を目標）**:
```markdown
# [プロジェクト名]

## コンパクション後の復帰手順
コンパクション直後は必ず:
1. この CLAUDE.md を再読
2. [ヒアリングから導出したプロジェクト固有の復元アクション]

## 目的
[ヒアリング回答2〜3から簡潔に記述]

## [ヒアリングで必要と判断したセクションのみ追加・最大3セクション]
```

**注意**: ~/.claude/CLAUDE.md に記載済みの内容（日本語応答、tmp/使用、Windowsパス規約、encoding注意）はここに書かない。

**settings.json（必須）**:
```json
{
  "env": {
    "CLAUDE_AUTOCOMPACT_PCT_OVERRIDE": "70"
  }
}
```

Tier 2として条件付き追加:
- `"ENABLE_TOOL_SEARCH": "auto:10"` — MCPが5個以上の場合
- `hooks.Notification` — Windowsで長セッションの場合（PowerShell MessageBox）

## Mode 2: ヘルスチェック

### クロスプロジェクト分析（最初に実行）

`~/projects/` の全プロジェクトのCLAUDE.md冒頭30行を読む。詳細確認が必要なペアのみ全文読み込む（コンテキスト効率のため）。

検出対象:
- **重複プロジェクト**: 目的が重複するペア → 統合を提案
- **肥大化**: CLAUDE.md 150行超 → 分割を提案
- **非アクティブ**: 30日以上変更なし → アーカイブを提案

### Tier別チェック項目

**Tier 1（必ず実行）**:

| # | チェック | 基準 | Auto-fix |
|---|---------|------|----------|
| 1 | CLAUDE.md行数 | <100行 | 分割提案 |
| 2 | コンパクション復帰手順 | 存在すること | 追加可 |
| 3 | auto-compact設定 | 存在すること | 追加可 |
| 4 | グローバル設定との重複 | 重複なし | 指摘のみ |

**Tier 2（プロジェクト特性に応じて実行）**:

| # | チェック | 条件 | Auto-fix |
|---|---------|------|----------|
| 5 | .claudeignore | バイナリ成果物がある場合 | 生成可 |
| 6 | Hooks設定 | 長セッション運用の場合 | 提案のみ |
| 7 | ENABLE_TOOL_SEARCH | MCP5個超の場合 | 追加可 |
| 8 | rules/ | 複数セッション運用の場合 | 提案のみ |

**クロスプロジェクト**:

| # | チェック | Auto-fix |
|---|---------|----------|
| 9 | 重複プロジェクト | 統合提案 |
| 10 | 150行超CLAUDE.md | 分割提案 |
| 11 | 30日以上非アクティブ | アーカイブ提案 |

### 診断レポート形式

```
========================================
ヘルスチェックレポート [date]
========================================

🔴 要対応: [問題項目]
🟡 確認推奨: [注意項目]

```

## Mode 3: 更新モニター

```bash
claude --version
```

WebFetchまたはCHANGELOGで前回確認バージョンからの差分を確認する。

```
更新モニターレポート v[前回] → v[現在]
---
📌 設定に影響する可能性がある変更:
  [変更内容] → [影響する設定] → 移行推奨度: 高/中/低

🔄 陳腐化候補:
  [カスタム機能]: [ネイティブ機能で代替可能になった理由]

⚙️ PreCompact Issue #14160:
  [未解決: 現状維持 / 解決済み: 移行手順を提案]
```

承認後、該当するプロジェクトの settings.json / CLAUDE.md を更新する。

---

*設計原則: 各要素を入れる理由を説明できること。Tier 1は常に適用、Tier 2はヒアリングから推論、Tier 3は求められた場合のみ。*
