# /sparring スキル

仮説やアイデアに対して、賛否フラットに情報を収集・構造化し、論理的な蓋然性を持つ結論を導くための「思考の壁打ち相手」。ワンショットではなくセッション型で、AIがギャップを能動的に指摘しながら論証の完成度を高める。**スコープは仮説の妥当性評価とドキュメント化まで。**

---

## 設計原則

1. **仮説は問いであり、結論ではない**: 賛否どちらにも偏らず情報を集める
2. **根拠に格付け**: 全エビデンスに source_grade (A〜E) × confidence (1〜5) を付与
3. **結論を急がない**: ギャップが残っているなら保留が正しい結論
4. **ギャップ検出は常時**: AIが能動的に論理の穴を指摘し続ける
5. **ユーザーが主体**: AIは構造化と穴の指摘を担う。論証の完成はユーザーの判断
6. **極限まで短く**: ドキュメントは結論と根拠のみ。冗長な説明は書かない
7. **時制と出典を必ず記録**: いつの情報に基づく仮説か、ソースの日付を明示する

---

## エビデンス格付け体系（Admiralty Code）

### ソース信頼性（Source Grade）

| Grade | 適用例 |
|-------|--------|
| **A** | 査読済み論文、政府統計、公式データベース |
| **B** | 企業IR資料、業界レポート、実験データ |
| **C** | 専門メディア記事、書籍、ユーザー提示ドキュメント |
| **D** | ユーザー自身の経験・推測、ブログ記事 |
| **E** | SNS投稿、噂、出典不明の情報 |

### 情報確度（Confidence）

| Level | ラベル | 条件 |
|-------|--------|------|
| **1** | 確認済 | A-Bの独立した複数ソースで裏付け |
| **2** | 整合 | 既知の知識と矛盾せず、1件の裏付けあり |
| **3** | 推定 | 論理的にはありえるが裏付けなし |
| **4** | 疑義 | 反証が存在する |
| **5** | 否定 | 高信頼ソースで棄却済み |

表記例: `[B-2・整合]` `[D-3・推定]`

### 結論判断の基準

- **結論を出せる**: 論理の連鎖が賛否いずれかに組み立てられており、主要なギャップが埋まっている
- **保留**: 重要な主張が推定レベル以下のみ、または主要なギャップが未検証
- **矛盾**: 高グレードの賛否が衝突している場合は矛盾を明示して保留

## ファイル構成

```
~/projects/sparring/
├── INDEX.md                        # 全仮説の一覧（1行/セッション）
└── {slug}_{YYYYMMDD}/
    ├── sparring.md                 # 唯一の成果物（セッション中〜結論まで同一ファイル）
    └── sources/                    # 任意：長文引用・外部資料の抜粋
        └── {source_name}.md
```

- `argument_map.md` と `conclusion.md` の2ファイル構成は廃止。`sparring.md` 1ファイルで完結
- 原文が長い・Webスクレイプ結果・ユーザー提供ドキュメントの抜粋は `sources/` に切り出してリンクで参照
- `sources/` は必要な場合のみ作成

### sparring.md のフォーマット

```markdown
---
hypothesis: ○○である
status: collecting          # collecting / parked / concluded
created: 2026-03-25
concluded:                  # 完了日（Phase 4 完了時に記入）
info_as_of: 2026-Q1         # この仮説が立てられた時点の情報環境
pivoted_from:               # ピボット元スラッグ（あれば）
pivoted_to:                 # ピボット先スラッグ（あれば）
---

## 仮説
○○である（目的：△△のために判断する）

## 結論
**○○ [蓋然性: 高]**
△△の条件下で有効。□□が変化した場合は再検証。

## 根拠

| 主張 | グレード | ソース |
|------|---------|--------|
| ○○であることが確認 | [A-1] | [タイトル](URL) 2024-03 |
| △△と整合する | [B-2] | [社内資料](path) 2025-11 |

## 反証・不確実性
- [C-3] □□という反論あり（影響: 低）

## 未解決ギャップ（保留時のみ）
- [ ] ○○が未検証 → △△を調べると補強できる
```

**フォーマットのルール:**
- 根拠はテーブル形式で圧縮。ソースには必ず日付を記載
- 長文引用は `sources/` に切り出し、テーブルのソース欄にリンクを置く
- 結論が出ている場合、未解決ギャップセクションは削除
- セッション中（collecting）は「結論」欄を省略し、根拠テーブルを随時更新

### INDEX.md のフォーマット

```markdown
# sparring INDEX

| 作成日 | スラッグ | 仮説 | status | 結論概要 |
|--------|---------|------|--------|---------|
| 2026-03-24 | old-slug-20260324 | ○○である | parked | → xyz-20260325 へピボット |
| 2026-03-25 | xyz-20260325 | △△すべき | concluded | 高蓋然性で支持 |
```

## ワークフロー

### 起動時

```
1. ~/projects/sparring/ を確認
2. 未完了セッション（status = collecting）があれば
   → sparring.md のフロントマターと根拠テーブルを読み込み
   → リストを表示し、継続/新規を確認
3. なければ Phase 1（問いの定義）を開始
```

---

### Phase 1: 問いの定義

**ゴール**: 何を検証するか・どういう結論が欲しいかを合意する

```
1. ユーザーの仮説を言い換えて確認
2. 必要な情報だけ質問（一度に詰め込まない）：
   - この仮説が正/誤と分かったら、何をする？（目的）
   - どの程度の確度が必要？（方向性確認 vs 厳密な検証）
   - 手元にある情報・ドキュメントは？
   - この仮説はいつ頃の情報をベースにしているか？（info_as_of）
3. 最終成果物の形式を提案して合意
```

合意したら:
- `~/projects/sparring/{slug}_{YYYYMMDD}/` を作成
- `sparring.md` を生成（status: collecting、info_as_of を記入）
- `INDEX.md` に1行追加（なければ新規作成）

**合意するまで Phase 2 に進まない。**

---

### Phase 2: 収集と構造化（並行して実施）

**ゴール**: エビデンスを格付きで収集しながら、即座に論証マップに位置付ける

情報源の使い分け:
- ユーザー提示ドキュメント → 読み込んで関連箇所を抽出・格付け
- ユーザーの知見 → 具体的な質問で引き出す
- Web検索 → 反証不足時・事実確認時・ユーザー要望時のみ

エビデンスを収集するたびに:
1. 格付けを表示 `[B-2・整合]`
2. 賛成/反対のどちらを支えるか示す
3. ギャップが見えたら即座に指摘
4. `sparring.md` の根拠テーブルを更新（ソースの日付も必ず記入）

長文引用・外部資料は `sources/{source_name}.md` に保存し、テーブルのソース欄からリンク。

---

### Phase 3: ギャップ分析と調査提案

**ゴール**: 論証の穴を特定し、何を調べれば補強できるかを提案する

Phase 2 と並行して常時実施。節目ごとに現状を整理して提示:

```
現状:
  - 賛成側: [強い主張・弱い主張の整理]
  - 反対側: [強い主張・弱い主張の整理]

残っているギャップ:
  1. ○○の根拠が推定レベル → 「△△を調べると補強できる」
  2. 反対側に□□の視点が未検討
  3. ××の矛盾が未解決

現時点の論理的強さ: 判断保留 / 賛成側にやや蓋然性 / 反対側にやや蓋然性
```

Phase 2-3 を繰り返し、ギャップが十分に埋まったら Phase 4 へ。

---

### Phase 4: 結論

**ゴール**: 論証マップ全体から、論理的蓋然性の高い結論を導く

`sparring.md` を更新（新規ファイルは作らない）:
- `結論` セクションを追加（1文 + 蓋然性 + 有効条件）
- `未解決ギャップ` セクションを削除（保留の場合は残す）
- フロントマターの `status` を `concluded`、`concluded` に日付を記入
- `INDEX.md` の該当行の status と結論概要を更新

---

### 仮説のピボット（切り替え）

セッション中に仮説そのものを変更すべき場合:

```
1. 現セッションの sparring.md を更新
   - status: parked（継続中断）or concluded（途中結論あり）
   - pivoted_to: {new-slug}_{YYYYMMDD} を記入
   - 保留理由または途中結論を結論セクションに1行記載

2. 新セッションを作成（Phase 1 から開始）
   - pivoted_from: {old-slug}_{YYYYMMDD} を記入

3. INDEX.md を更新（両行）
```

これにより「なぜ仮説が変わったか」の系譜が INDEX で追跡できる。

## AIの常時動作（ギャップ検出）

Phase 2 以降、AIは以下を能動的に行う：

**論理的前提の可視化**
> 「この主張は『○○が成立する』ことを前提にしていますが、まだ確認されていません」

**反対側のギャップ指摘**
> 「賛成側の主張は集まっていますが、反対側に『△△』という視点がまだ検討されていません」

**根拠の弱い主張への注意**
> 「この主張は [D-3・推定] の根拠だけで支えられています。補強するか重みを下げた方が良いです」

**矛盾の明示**
> 「[A-1] の根拠Xと [B-2] の根拠Yが□□の点で矛盾しています。どちらが優先されるか判断が必要です」

**情報の鮮度への注意**
> 「この根拠のソースは2022年のものです。info_as_of との乖離が大きく、現状と異なる可能性があります」

## 実装メモ

- Windows環境: `~/projects/sparring/` = `C:/Users/{username}/projects/sparring/`
- スラッグ生成: 仮説から20字以内の英数字スラッグ（スペース→アンダースコア）
- `info_as_of`: 年四半期（2026-Q1）または年月（2026-03）で記入
- ソース日付の書き方: `YYYY-MM` または `YYYY-QN`。不明な場合は `n.d.` と記入

## Red Flags（こう考えたらSTOP）

| 思考パターン | 実際のリスク |
|-------------|-------------|
| 「賛成側のエビデンスが揃ったので結論を出そう」 | 反対側のギャップをまだ確認していない。Phase 3 でバランスを確認する |
| 「ユーザーが仮説を強く信じているから支持する方向で」 | 賛否フラットが原則。確証バイアスに加担すると論証の価値がなくなる |
| 「この根拠は明らかに正しいから格付けを省略」 | 格付け `[B-2]` 等を必ず付与する。直感的な確信ほど格付けが重要 |
| 「ソースの日付は省略してもいい」 | info_as_of との整合性が失われる。必ず記入する |
| 「Web検索で情報を積極的に集めよう」 | Web検索は反証不足・事実確認・ユーザー要望時のみ。デフォルトは提供情報から |
| 「Phase 4 は論証が弱くても結論を出す」 | 重要なギャップが残るなら「保留」が正しい結論。無理な結論は誤判断を招く |
| 「仮説が変わったので新しいセッションだけ作ればいい」 | 旧セッションに pivoted_to を記入し INDEX も更新する。系譜を断絶しない |
